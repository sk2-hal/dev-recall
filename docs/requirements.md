# DevRecall 要件定義

## 目的

AI Agentを使ったソフトウェア開発の全工程を、Codexを実装Agentとして1〜2週間で体験する個人学習プロジェクト。要件整理、設計、小さな実装、自動テスト、Gitでの差分レビュー、Web公開まで進める。

利用者はC#/.NETの経験があり、Nuxt/TypeScriptは学習中。重要な設計判断と実装内容は、理由とともに説明する。

## 製品の考え方

AI支援開発で得た判断・問題・解決・学びを、日記ではなく再利用可能な知識単位「Entry」としてProject別に蓄積・検索する。1つのEntryでは1つの知識を扱う。ProblemとSolutionは別Entryにする。Entry相互リンクはv0.2以降。

## 優先順位

### Must：MVPの完了に必要

- Projectを作成し、一覧から選択できる。
- Project内でEntryを作成・一覧表示・詳細表示・編集できる。
- Entryに固定Typeを複数設定できる：Decision / Problem / Solution / Learning / Note（保存値はdecision / problem / solution / learning / note）。Noteは他の4種類に分類しにくい汎用メモ用とする。
- Entryに自由なTagを複数設定できる。
- Project内のEntryをタイトル・本文・タグのキーワードで検索できる。
- Project、Entry、Type・Tagとの関連をDBに永続化する。
- ブラウザから利用でき、公開環境にデプロイする。
- 最低限の自動テストを用意する。

### Should：Must完了後

AIチャットを利用者が貼り付け、AIがEntry候補（タイトル・本文・Type・Tag）に構造化する。人間が確認・修正してから保存する。候補の自動保存はしない。AIサービスやモデルはこの段階で選定する。

### Could：余裕があれば

- Type / Tagによるフィルタ。
- 本文のMarkdown表示。
- Projectの説明。
- Entryの削除。

### MVP対象外

自動チャット履歴取込、GitHub連携、RAG・ベクトル検索・意味検索、QA（知識への質問応答）、共有機能、モバイル対応、他ツール連携。GitHubは開発用のコード管理に利用するが、製品機能としては連携しない。

## 画面

| 画面 | 主な操作 |
| --- | --- |
| Projects一覧 / 新規 | Project一覧、Project作成、Project選択 |
| ProjectのEntry一覧 | 一覧、キーワード検索、新規作成への移動 |
| Entry作成 | タイトル・本文・複数Type・自由Tagを入力して保存 |
| Entry詳細 / 編集 | 保存内容を確認し、編集・再保存 |

## 認証と公開データ

MVPでは認証を実装しない。公開デモには公開可能なサンプルデータのみを使用し、秘密情報、認証情報、非公開の業務情報を保存しない。チャット貼付にも同じ制約を適用する。

認証のない公開環境では、URLを知る第三者もデータの閲覧・作成・編集が可能になる前提とする。個人用の非公開保管庫としては使用しない。共有・権限管理機能の実装は対象外。

## MVP受け入れ条件

1. Projectを作成し、そのProjectに複数Typeと自由Tag付きのEntryを保存できる。
2. 一覧からEntry詳細を開き、編集後の内容が再読み込み後にも保持される。
3. タイトル・本文・タグのそれぞれに含まれるキーワードでEntryが見つかり、別ProjectのEntryは混ざらない。
4. ブラウザを閉じて再アクセスしても保存済みデータが保持される。
5. 公開URLから主要操作ができ、最低限の自動テストが通る。

## 実装順序

基盤・DB → Project作成 → Entry作成 / 一覧 / 詳細 → 編集 / 検索 → 自動テストと公開確認 → ShouldのAI構造化。テストは各変更に合わせて追加し、最後にまとめて後付けしない。1〜2週間に収めるため、Mustを優先してShould / Couldは切り離す。

## STEP 6-7の範囲

EntryのDB設計と作成APIを実装する。Typeは上記5種類を1件以上・重複なしで保持する。本文名はbody、Typeはtext[]とする。TagとEntry画面・一覧・編集・検索は後続STEPで扱う。EntryがあるProjectの削除は拒否し、自動削除しない。

## STEP 6-12の範囲

利用者の指定により、CouldのEntry削除をこのSTEPで実装する。詳細画面で確認後に削除し、Projectの一覧へ戻る。キャンセルでは削除しない。認証なしの公開環境では第三者も削除できる前提は既存の公開データ方針に従う。

## STEP 6-13の範囲

Project内のタイトル・本文キーワード検索を実装する。Tag自体が未実装のためTag検索は後続STEPとし、Mustの最終要件には引き続き含める。検索語は前後空白を除いた全体を1つの語として扱い、空欄は一覧表示に戻す。

## STEP 6-14の範囲

TagのテーブルとEntry APIを実装する。Tag名は前後空白を除き、空の要素と重複を除外して全Project共通の同名Tagを再利用する。POSTで省略したTagは空、PATCHで省略したTagは維持し、明示的な空配列で関連を解除する。Entry削除はその関連だけを削除し、共有Tagは残す。Tag入力・表示UIおよびTag検索は後続STEP。Mustの受け入れ条件全体が完了したことを意味しない。

## STEP 6-15の範囲

Entry作成・編集で任意の複数Tagを追加・削除し、一覧・詳細で表示する。既存Tagの編集、全解除、保存失敗時の入力保持に対応する。Tagキーワード検索は後続STEP。

## STEP 6-16の範囲

Project内のキーワード検索でタイトル・本文に加えて関連Tag名も検索対象とする。複数Tagに一致したEntryも1件として表示する。実DBと公開環境の受け入れ確認は後続作業。

## STEP 7：MVP UI・UX仕上げ

Entry追加を一覧先頭に配置し、一覧・検索の件数と空状態の次の操作を案内する。入力項目の説明を補い、既存の読み込み・エラー・再試行・保存中の操作制限を維持する。Mustの検索はタイトル・本文・Tagのキーワード検索で満たし、CouldのType / Tag選択式フィルタは追加しない。

以後は元の全体ロードマップに戻す。STEP 6-13〜6-16はTagと検索を分割して実装した履歴として残し、STEP 6-17は設けない。STEP 7の次はSTEP 8（総合テスト・実DBを含む品質確認）、STEP 9（Vercel + Neon本番環境）、STEP 10（Web公開・最終確認）とする。

STEP 8の自動検証・開発DB受け入れ確認に加え、STEP 9の本番DB適用・Vercelデプロイ、STEP 10のユーザーによる公開環境の主要操作・保存保持確認が完了し、Must要件を達成した。各STEPの「後続作業」は当時の記録として残す。結果と未検証の並行更新・rollbackは[acceptance.md](./acceptance.md)、公開構成は[deployment.md](./deployment.md)を参照。Should / Couldの追加は別の作業として扱う。
